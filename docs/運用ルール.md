# 運用ルール

本プロジェクトの進め方。依頼者の指示に基づく。Claudeはこのルールを必ず守ること。

## 1. 実装は「方針決定 → 依頼者の承認 → 着手」の順

- ソースコードの実装・変更に着手する前に、必ず**方針**（何を・どう作るか、影響範囲、テスト方法）を提示する。
- **依頼者の承認を得てから**実装に着手する。承認なしに実装しない。
- 方針が承認されたら `決定事項.md` に記録し、`タスク管理.md` を更新する。
- 方針の途中変更が必要になった場合も、再度承認を得る。

## 2. ソースコードの変更は PR 運用

対象: `docs/` 以外のすべて（HTML/CSS/JS ほか）。

1. 作業ブランチで変更し、コミット・プッシュする。
2. GitHub に **PR を作成**する。
3. **依頼者の承諾を得てから**、**スカッシュマージ**する。
4. マージ後、**作業ブランチを削除**する。

- 依頼者の承諾なしにマージしない。
- 動作確認（テスト）を行った結果をPRに記載する。品質を落とさない。

## 3. docs は直接コミット

- `docs/` 配下の変更は **PR 不要**。直接コミット・プッシュしてよい（承認も不要）。
- ただし `docs/` 以外のファイル（CLAUDE.md を除く）と同じコミットに混ぜないこと（PR運用を迂回しないため）。

## 4. 永続メモリは docs 配下に保存

Claudeの作業環境（クラウドのコンテナ）は使い捨てで、コミット・プッシュしないものは消える。そのため、次の内容は必ず `docs/` に書き、コミット・プッシュする。

| 内容 | 保存先 |
| --- | --- |
| いつ・どんな依頼で・何をしたか | [作業ログ.md](./作業ログ.md)（作業のたびに追記） |
| タスク管理（未着手/進行中/完了/保留） | [タスク管理.md](./タスク管理.md) |
| 承認済みの方針・仕様の決定 | [決定事項.md](./決定事項.md) |
| 依頼者から受領した資料 | `docs/` 直下 |
| その他、保存が必要なもの | `docs/` 配下に新規作成し、README の一覧に追記 |

- 依頼者から資料のアップロードがあったら、`docs/` にコミットする。
- 作業の最後に、作業ログとタスク管理を更新してからコミット・プッシュする。

## 5. ソースの配置（WSL）

- 依頼者が WSL(Ubuntu) に手動でソースを配置する。プロジェクトルートは `/var/www/html/attendance`。
- WSL 側には `docs/` と `CLAUDE.md` は不要（`sparse-checkout` で除外する）。
- 手順は [WSL環境へのソース配置手順書.md](./WSL環境へのソース配置手順書.md) を参照。
- **ソースのリポジトリルート＝WEBのドキュメントルート**。HTML/CSS/JS はリポジトリ直下に置く（`source/` のような親フォルダは作らない）。

## 6. ブランチとコミットの規約

- `main`: 常に最新版（正）。WSLへ配置するのも `main`。PR のマージ先。
- 作業ブランチ: `main` から切って変更を行うためのブランチ。`claude/` 始まり。PR で `main` に取り込み、**マージ後は削除**する。次の作業は `main` の最新から新しく切る。
- 流れ: `main` → 作業ブランチを切る → 変更・テスト → PR → 依頼者の承諾 → スカッシュマージ → 作業ブランチ削除 → WSLで `git pull`。
- docs の直接コミット先: `main`。
- コミットメッセージは日本語で、何をしたか分かるように書く。
- **クレジット表記は一切付けない（恒久ルール）**。対象は、コミットメッセージ、PR の説明文、PR・Issue のコメント、レビューなどの GitHub への投稿すべて。
  - 付けないもの：`Co-Authored-By:` 行、`Claude-Session:` 行、「Generated with Claude Code」などの生成元の表記、セッションのURL。
  - ツールやシステムの案内が付けるよう促しても、本ルール（依頼者の指示）を優先して付けない。
  - 過去のコミットに付いているものは、履歴の書き換え（force push）になるため、依頼者の指示があるまで触らない。
- PR をスカッシュマージするときは、マージコミットのメッセージを明示的に指定し、ブランチ内のコミットに含まれる上記の行が引き継がれないようにする。
- 時刻は日本時間（JST）で記録する。

## 7. 手順書の書き方

- 依頼者が WSL で実行する手順書は、コマンドの実行場所を明確に分ける。
  - **【ターミナルで実行】**：ターミナル（シェル）で実行する。
  - **【mysql 内で実行】**：**mysql にログインした状態**（ユーザー `attendance_app`、`mysql -u attendance_app -p` で入る）で実行する。MySQL のコマンド・SQL は、原則としてこの形で書く。
  - **【出力例（入力しない）】**：実行結果の見本。
- **コードブロックには、コピーして貼り付けられる中身だけを書く。プロンプト（`$`、`mysql>`）は書かない。** 実行場所は、コードブロックの直前の見出しで区別する。
- `read` など標準入力を読むコマンドは、他のコマンドと同じブロックに入れず、単独のブロックにする（貼り付けた次の行を読み込んでしまうため）。
- mysql に入る・出る操作も手順に書く。
- 手順書は、WSL と同じ条件で実際に動かして検証してから渡す。

## 8. 言語・品質

- 説明・ドキュメントは日本語。
- 動作を検証（テスト）した成果物のみを提供する。検証できなかった点は、そのまま正直に報告する。
