### 2-2. アカウント作成の、エラーを出す順番（`validateAccount()`）

- 今：コメントは「画面の順」だが、確認の順番は「氏名 → メールアドレス → 部署 → …」。画面の並びは「氏名 → 部署 → メールアドレス → …」なので、部署とメールアドレスの両方が誤っているとき、画面で下にあるメールアドレスの誤りが先に出る。
- 直し方：**確認の順番を、画面の並びに合わせる**（氏名 → 部署 → メールアドレス → 入社日 → 権限 → 承認範囲 → パスワード → 確認）。画面の一番上の誤りから順に出るようになる。コメントはそのまま正しくなる。
- 入力のルール（何が誤りか）は変わらない。順番だけが変わる。

### 2-3. 自動ログアウトのあとに「ログアウト」を押すと、400 の画面になる（`logout.php`）

- 起きること：2時間操作が無いと、`startAppSession()` がログイン状態と一緒に CSRF トークンも消す。そのあと画面の「ログアウト」を押すと、トークンが合わず「不正なリクエストです。」（400）の画面になる。
- 直し方：**すでにログアウトしている（セッションにログインの情報が無い）ときは、CSRF の確認をせずに、ログイン画面へ移す**。ログイン画面には「一定時間操作がなかったため、ログアウトしました。」が出る（今のしくみのまま）。
- 安全性：ログインしていない人を「ログアウト」させても、何も起きない（悪いサイトから送られても害が無い）ので、CSRF の確認を省いてよい。ログイン中のログアウトは、今までどおり CSRF を確かめる。

### 2-4. ログイン画面を長く開いたままにすると、ログインで 400 になる（`login.php`）

- 起きること（2-3 と同じ原因）：ログイン画面を開いたまま長く（2時間以上）置くと、サーバー側のセッションが消え、CSRF トークンも無くなる。そのあと「ログイン」を押すと、400 の画面になる。
- 直し方：ログイン画面では、CSRF トークンが合わないとき、400 の画面ではなく、**同じログイン画面に「画面の有効期限が切れました。もう一度ログインしてください。」を出す**（新しいトークンで、そのまま入力し直せる）。
- 安全性：トークンが合わない送信は、今までどおりログインの処理をしない。出す画面が変わるだけ。

### 2-5. 簡単残業申請のあとも、ボタンが押せるまま（`index.php`・`js/main.js`・`api/attendance.php`・`src/attendance.php`）

- 起きること：申請が通ったあとも「簡単残業申請」のボタンが押せる。もう一度押すと、DB の一意制約で「本日分の残業申請は、すでに申請中です。」と断られる（データは壊れない）。画面を読み込み直しても、押せるまま。
- 直し方：
  1. **今日の残業申請が申請中なら、ボタンを押せなくする**。サーバーが判断する（`attendanceView()` に「残業申請が申請中か」を渡す。画面の最初の表示と、出退勤のボタンを押したあとの表示の両方）。
  2. その間、ボタンの下の案内を「本日分の残業申請は申請中です。」にする。
  3. 申請が通った直後も、JavaScript がすぐにボタンを押せなくし、案内を変える（読み込み直さなくても）。
- 承認・却下されたあとは、また押せるようになる（今のルールのまま：申請中の重複だけを防ぐ。BR-002）。
- 「申請中か」は、今ある `fetchMonthlyRequests()` で調べる（今日の修正申請の確認 `isCorrectionPending()` と同じ形）。**SQL の追加・変更は無い**。

### 2-6. 承認なのに、長いコメントで断られる（`src/approvals.php` の `reviewRequest()`）

- 起きること：コメントの長さ（500 文字まで）の確認を、承認か却下かを見る前に行っている。画面からは承認のときにコメントを送らないので起きないが、API に直接「承認＋長いコメント」を送ると、承認なのにコメントの誤りで断られる。
- 直し方：コメントの長さは、**却下のときだけ**確かめる（承認のときは、コメントを使わない）。
