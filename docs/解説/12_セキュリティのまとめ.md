# 12. セキュリティのまとめ

このシステムで行っている対策を、攻撃の種類ごとにまとめる。詳しい説明は、各章を参照。

| 攻撃・危険 | どんなことが起きるか | 対策 | どこで | 章 |
| --- | --- | --- | --- | --- |
| SQL インジェクション | 入力で SQL の意味を変えられ、データを盗まれる・消される | プレースホルダと `bindValue`、`ATTR_EMULATE_PREPARES => false` | `src/queries/` 全部 | 4 |
| XSS（クロスサイトスクリプティング） | 入力した `<script>` が他人の画面で動く | PHP は `h()`、JavaScript は `textContent`。社員の勤怠では、管理者の画面に他人の氏名・申請の理由が出るので、特に大事（`pr10.js` で `<script>` が文字のまま出ることを確かめている） | 全画面 | 2・10・13 |
| CSRF | 悪いサイトから、勝手に操作を送られる | CSRF トークン、Cookie の `SameSite=Lax`、更新は POST だけ | `src/session.php`、全部の POST | 2 |
| セッション固定・盗み見 | 他人のセッション ID で入り込まれる | ログイン時に ID を作り直す、`use_strict_mode`、Cookie の `HttpOnly` | `src/auth.php`、`src/session.php` | 2・3 |
| パスワードの漏洩 | DB が漏れたら、パスワードが分かる | `password_hash()` で保存し、`password_verify()` で照合 | `src/auth.php`、`src/admin.php` | 3・9 |
| ID の存在の調査 | ログインの返事や、社員の勤怠の詳細の返事から、存在する ID・退職した人が分かる | 失敗の理由を区別しない、ID が無くても照合して時間をそろえる。社員の勤怠の詳細は、範囲外・存在しない・自分・退職をどれも同じ 404 と同じ文にする | `src/auth.php`、`members/detail.php`（`MEMBER_NOT_VIEWABLE_MESSAGE`） | 3・13 |
| 権限の無い操作 | URL を直接開く・API に直接送る | 画面と API の両方で、サーバー側で権限と範囲を確かめる | `requireRole()`、`canReview()`、`findManagedAccount()` | 3・8・9 |
| 他人の記録ののぞき見 | 社員の勤怠の詳細の URL の `id` を書き換えて、範囲外の社員の記録を見る | 管理者だけ（`requireRole()`。社員・システム管理者は 403）。詳細でも一覧と同じ条件（承認範囲・自分でない・在籍中）を毎回確かめる。在籍状態が分からないときは見せない | `members/detail.php`、`canViewMember()` | 13 |
| 見るだけの画面からの操作 | 社員の勤怠の詳細から、その社員の申請を送る | 詳細には申請の API の URL・CSRF トークン・ボタンを出さない。申請の API は本人の分しか受け付けない | `templates/calendar.php`（`$readOnly`）、`calendarDays()`、`api/requests.php` | 7・13 |
| 入力の改ざん | 画面の制限（`min`・`disabled`）を外して送る | 入力のルールと「押せるか」は、すべてサーバーで確かめる | `src/*.php` の validate・`actionMode()` | 5・7 |
| 同時の操作 | 二重に記録・承認される | DB の一意制約、`SELECT … FOR UPDATE`、トランザクション | `attendances`・`attendance_requests`・採番 | 4・8・9 |
| 内部のファイルの公開 | `src/dbconnect.php`（パスワード）や `.git` が見える | Apache の設定で `src/`・`docs/`・`tests/`・`.git` などを拒否 | `docs/apache/attendance.conf` | 1 |
| エラーの中身の表示 | エラーの文から、内部の作りが分かる | 画面には定型の文だけ、詳しくはログへ | `src/errors.php`、`src/dbconnect.php` | 2 |
| 席を離れたままの放置 | 他人にそのまま使われる | 2時間操作が無ければ、自動でログアウト | `src/session.php` | 2・3 |
| 無効にした人の利用 | 退職した人がログインしたまま使う | 画面を開くたびに DB で利用可否を確かめる | `currentUser()` | 3 |

## このシステムで、あえてしていないこと

| 項目 | 理由・今後 |
| --- | --- |
| ログインの失敗回数の制限（アカウントのロック） | 今回は含めない（DB設計書 P-8）。社外に公開するなら検討する |
| HTTPS | WSL の中だけで使うため。社外に公開するなら必須（Cookie の `secure` は、HTTPS のときに自動で付く作り） |
| DB の接続情報をリポジトリの外に置く | 学習用で非公開のため、`src/dbconnect.php` に書いている（D-045）。公開するなら、環境変数などに移す |
| 位置情報・不正登録の対策 | 要否が未定（決定事項の「未決定」） |

## 新しくコードを書くときの確認リスト

- [ ] 画面に出す値は `<?= h(…) ?>` で出したか（JavaScript なら `textContent`）。
- [ ] SQL の値はプレースホルダで渡したか（文字列をつなげていないか）。
- [ ] 更新は POST で、`requireValidCsrfToken()` を呼んだか。
- [ ] `requireLogin()`（API なら `currentUser()`）と、権限のチェックをしたか。
- [ ] URL や送られた ID のもの（申請・社員など）を、この人が見て・触ってよいか、サーバーで毎回確かめたか（一覧に出していることは守りにならない）。
- [ ] 入力のルールを、サーバー側で確かめたか。
- [ ] 2つ以上の更新は、トランザクションでまとめたか。
- [ ] CSS・JS は `assetUrl()` で読み込んだか。
