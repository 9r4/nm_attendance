# 11. テスト

主なファイル：`tests/*.php`（PHPUnit）、`docs/検証スクリプト/`（ブラウザでの確認）、`composer.json`

このシステムでは、3種類のテストで「動くこと」を確かめてから PR を出している。

| 種類 | 道具 | 確かめること | 実行する人 |
| --- | --- | --- | --- |
| 単体テスト | PHPUnit | 計算・ルールの関数（DB を使わない） | Claude（WSL でも `composer test` で実行できる） |
| DB を使うテスト | PHPUnit＋テスト用の DB | SQL の関数、トランザクション、同時の操作 | Claude（テスト用の DB を作り直すので、WSL では実行しない） |
| ブラウザでの確認 | Playwright | 実際に画面を操作した結果 | Claude |

2026-10-26 時点（PR 10 を入れたあと）で、PHPUnit 116 件、ブラウザの確認 402 項目（pr3 36・pr4 41・pr5 58・pr5補足 20・pr6 50・pr7 90・pr8 19・pr9 20・pr10 68）。Claude の環境は、依頼者の WSL と同じ版（Apache 2.4.66・PHP 8.5.4・MySQL 8.4.11）で動かしている（[検証スクリプト/README.md](../検証スクリプト/README.md)）。

## 11-1. 単体テスト（PHPUnit）

例：`tests/AdminTest.php` の社員コードの作成のテスト。

```php
public function testFormatEmployeeId(): void {
    $this->assertSame('2026001', formatEmployeeId(2026, 1));
    $this->assertSame('2026999', formatEmployeeId(2026, 999));
    $this->assertSame('2026A01', formatEmployeeId(2026, 1000));
    $this->assertSame('2026Z99', formatEmployeeId(2026, 3573));
    …
}
```

- `assertSame(期待する値, 実際の値)`：同じでなければ、テストが失敗する。
- 名前が `test` で始まるメソッドが、1つのテストになる。
- **境目の値**（999 と 1000、上限の 3573、範囲を1つ超えた 3574 など）を必ず試す。誤りは境目で起きやすいため。

### データを変えて繰り返す（データプロバイダ）

```php
#[DataProvider('workTimes')]
public function testDailyWorkMinutes(array $row, ?int $expected): void {
    $this->assertSame($expected, dailyWorkMinutes($row, '2026-10-15', self::SETTINGS));
}
```

`workTimes()` が返す組み合わせ（「休憩なし」「昼休憩と休憩が重なる」「13:30 出勤」…）ごとに、同じテストを繰り返す。テストのメソッドは 66 個だが、件数が 116 件になるのはこのため。

### 実行のしかた（WSL でも可）


## 11-2. DB を使うテスト

`tests/ApprovalsDbTest.php`・`tests/AdminDbTest.php`・`tests/MembersDbTest.php` は、テスト用の DB（`attendance_test`）を使い、**依頼者が書いた SQL の関数を、本物の MySQL で**確かめる。

- テストのたびに、表を全部消して `schema.sql` と `test_data.sql` から作り直す（前のテストの影響を受けないように）。
- 普通には起こしにくい状況も作って確かめる：
  - **途中で失敗したら元に戻るか**：テスト用のトリガー（`SIGNAL SQLSTATE '45000'`）で、2つ目の更新をわざと失敗させ、1つ目も取り消されていることを確かめる。
  - **同時の操作**：接続を2つ作り、1つ目のトランザクションの途中で、2つ目が待たされること（ロック）を確かめる（社員コードの採番）。
  - **LEFT JOIN の条件の置き場所**：今日ではない日の勤怠だけがある社員を入れておき、社員の勤怠の一覧に、その社員が「勤怠の列が `null`」で出ることを確かめる（日付の条件を `WHERE` に書くと消え、`ON` に書き忘れると前の日の時刻が混ざる。13-2）。
  - **2つの条件の突き合わせ**：一覧の SQL（`fetchMemberAttendances()`）が選ぶ社員と、詳細を見てよい社員（`canViewMember()`）が同じになることを、テストデータの全員で確かめる。

## 11-3. ブラウザでの確認（Playwright）

`docs/検証スクリプト/pr3.js`〜`pr10.js`（と `pr5補足.js`）は、本物のブラウザ（Chromium）を動かして、画面を操作する。例は `pr10.js`（社員の勤怠）から。

```js
  await page.fill('#login_id', id); await page.fill('#password', pw);
  await Promise.all([page.waitForNavigation(), page.click('button[type=submit]')]);
```

```js
  check('社員のメニューに「社員の勤怠」なし', !(await menu(yamada)).includes('社員の勤怠'));
  check('社員は members/ が 403', (await yamada.goto(BASE + 'members/')).status() === 403);
```

- 入力して、押して、表示された文字や DB の中身を確かめる。
- 画面を通さずに API に送る確認（他人の申請・範囲外・CSRF が違う など）もしている。
- **新しい PR では、前の PR のスクリプトもすべて流し直す**。新しい変更で、前の機能が壊れていないか（「デグレ」が無いか）を確かめるため。PR 10 では記録表示のカレンダーを部品（`templates/calendar.php`）に移したので、記録表示の `pr4.js`・`pr5.js`・`pr5補足.js` を流し直して、見た目と動きが変わっていないことを確かめた。メニューに「社員の勤怠」が増えたので、`pr6.js` のメニューの項目の確かめも合わせて直した。

## 11-4. テストで見つかったもの（例）

テストは「動くことの確認」だけでなく、誤りを見つけるためにある。

- PR 6：処理済みの一覧の SQL に申請日時の列が抜けていて、日時が「1/1 09:00」になっていた（警告のログから発見し、テストを足した）。
- PR 6：選んでいるタブにマウスを乗せると、文字が見えなくなっていた（ブラウザでの確認で発見）。
- PR 7：採番の最初の案は、同時に作るとデッドロックになることが分かり、SQL を変えた。DB設計書の採番の例の番号のずれも見つけた。
